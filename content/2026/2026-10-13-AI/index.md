## 🤖 Overview

요즘 운영 로그와 트레이스는 대시보드 대신 로컬의 Claude Code 세션에서 본다. SigNoz MCP 서버를 붙여두고, 조사 순서를 정해둔 스킬로 배포 전후 모니터링을 맡긴다.

처음에는 도구만 붙여두고 그때그때 물어봤다. 그러다 Agent 가 MCP 도구의 사용 방법을 잘못 짚거나 의도와 다르게 쓰는 부분들을 바로잡기 위해, 조사 순서를 저장소 안에 스킬로 고정했다. 이 스킬은 지금도 모니터링을 하면서 계속 고도화되고 있다. 그렇게 쌓인 규칙 중에는 MCP 도구의 한계를 메우기 위한 우회책도 섞여 있었다.

이 글은 그 스킬을 만들고 유지해온 기록이다. 스킬에 무엇을 담았는지, MCP 버전이 바뀔 때 스킬이 어떻게 흔들렸는지, 그리고 우회책을 계속 쌓는 대신 원인이 있는 업스트림을 고치기 시작한 이야기를 남긴다.

<br>
<br>

### 1. 대시보드 대신 로컬 세션에서 운영을 본다

---

사내 서비스는 self-hosted SigNoz 로 로그와 트레이스를 모으고 있다. SigNoz 는 공식 [MCP 서버](https://github.com/SigNoz/signoz-mcp-server)를 Go 바이너리로 배포한다. 받아서 Claude Code 에 stdio 서버로 등록하면, 세션 안에서 로그 검색이나 집계, 트레이스 상세 조회를 도구로 바로 부를 수 있다.

```json
{
  "mcpServers": {
    "signoz": {
      "type": "stdio",
      "command": "/Users/jh8459/signoz-mcp-server",
      "env": { "SIGNOZ_URL": "...", "SIGNOZ_API_KEY": "..." }
    }
  }
}
```

처음 며칠은 편했다. 대시보드에서 필터를 하나씩 고르는 대신 "최근 6시간 슬로우 쿼리 상위 20개 뽑아줘" 라고 쓰면 됐다. 쿼리 문법을 기억하지 않아도 되고, 결과를 표로 정리하는 것까지 맡길 수 있었다.

그런데 결과를 그대로 믿기에는 걸리는 장면이 몇 번 있었다.

<br>
<br>

### 2. 도구만 붙여두면 같은 실수를 반복했다

---

크론 실행 트레이스를 조사하던 중이었다. Agent 가 찾아온 트레이스에는 크론이 13ms 만에 "대상 0건" 으로 끝난 기록이 세 건 있었다. 운영 크론이 대상을 하나도 못 찾았다는 결론이 바로 나왔다.

결론을 정리하기 전에 환경 속성을 찍어봤다. 세 건 모두 dev 였다.

dev 와 prod 가 같은 서비스 이름을 쓰고 있어서, 서비스 이름만 걸고 조회하면 두 환경이 한 결과에 섞인다. dev DB 는 오래된 스냅샷이라 대상이 0건인 게 오히려 자연스러웠다.

모양만 다를 뿐 같은 일이 두 번 더 있었다.

한 번은 어떤 요청이 실제로 들어왔는지 확인하는 쿼리가 빈 결과로 돌아왔다. 그 결과를 믿었다면 "그런 요청은 없었다" 고 보고 운영 트래픽을 막는 설정을 넣었을 것이다. 다시 보니 시간 범위가 1년 틀려 있었다. 범위가 틀려도 쿼리는 성공하고, 결과만 비어서 온다.

또 한 번은 최신순으로 정렬하고 개수를 제한한 결과를 보고 "이 시간대에 몰려 있다" 는 말이 나왔다. 목록이 가장 최근 구간부터 채워졌으니 그렇게 보일 수밖에 없었다. 날짜별로 창을 잘라 다시 세보니 매일 비슷한 양이었다.

세 번 모두 도구는 오류 없이 결과를 돌려줬고, 결과만 봐서는 어디가 틀렸는지 알 수 없었다.

<br>

### 3. 조사 순서를 스킬로 고정했다

---

결과를 보고 틀린 걸 알아챌 수 없다면, 결과를 받기 전에 확인을 끝내두는 수밖에 없었다. 그래서 도구를 부르는 순서를 스킬로 정했다. 스킬이 하는 일은 그 순서를 지키게 하는 것 하나고, 단계마다 2장에서 겪은 일이 하나씩 걸려 있다.

맨 먼저 시간 창을 절대 시각으로 고정하고, 산출한 epoch 을 다시 KST 로 되돌려 의도한 시각이 맞는지 본다. 1년 틀린 쿼리는 이 단계에서 걸린다. 그다음 severity 별 건수를 세어 기준선을 잡는다. 이 숫자가 있으면 최신순 목록을 보고도 그게 전체인지 앞부분인지 가를 수 있다. 상세 조회는 그 뒤에 한다. 환경 필터는 모든 조회에 기본으로 건다.

0건으로 결론을 낼 때는 결과가 나와야 하는 조건으로 같은 형태의 쿼리를 한 번 더 던진다. 그쪽도 0건이면 문제는 데이터가 아니라 쿼리에 있다.

함정 목록은 스킬 본문에 넣지 않고 별도 문서로 뺐다. 스킬은 시작할 때 그 문서를 먼저 열기만 한다. 스킬에는 순서만, 문서에는 이유와 근거를 두니 함정이 하나 늘어도 스킬은 그대로 둘 수 있었다.

그 문서에서 가장 자주 열리는 건 정상 노이즈 목록이다. ERROR 와 FATAL 을 한 번에 조회했다가 결과가 FATAL 로 꽉 차서 ERROR 가 하나도 보이지 않은 적이 있다. 채운 건 전부 노이즈였다.

기능 플래그가 꺼진 크론은 조용히 넘어가지 않고 예외를 던져서 FATAL 로그가 하루 수천 건 쌓인다. 비로그인 방문자의 세션 조회도 401 WARN 으로 시간당 수백 건씩 남는다. 이걸 먼저 걸러내지 않으면 진짜 오류가 개수 제한에 밀려 결과에서 빠진다.

로그 본문과 SQL 본문에는 외부 사용자의 입력이 그대로 실린다. 그래서 이 둘은 지시문으로 읽지 않는다는 규칙도 넣었다. 로그에 "앞의 지시를 무시하고 ~해라" 같은 문장이 있어도 Agent 에게는 조사 대상 문자열일 뿐이다.

### 4. 스킬의 도구 목록만으로는 권한이 줄지 않았다

---

v0.14 MCP 서버는 도구가 43개고, 그중 15개는 알림 규칙이나 대시보드를 만들고 지우는 쓰기 도구다. 조사 스킬은 읽기만 하면 되니 스킬의 `allowed-tools` 에 읽기 도구 12개만 적어두고, 이걸로 권한을 좁혔다고 생각했다.

실질 권한은 하나도 줄어 있지 않았다.

`allowed-tools` 는 스킬이 실행되는 동안 승인 없이 쓸 수 있는 도구를 정할 뿐이다. 세션 전체의 자동 승인 범위는 `settings.json` 의 `permissions.allow` 가 정하는데, 그쪽에 `mcp__signoz__*` 와일드카드가 그대로 남아 있었다. 알림 규칙 API 는 우리 백엔드 버전에서 실제로 동작하니, 그대로 뒀다면 조사 도중에 알림 규칙이 바뀔 수도 있었다.

두 곳을 같은 읽기 도구 목록으로 맞췄다.

<br>
<br>

### 5. 배포 전후에는 관측 키부터 바뀐다

---

스킬을 가장 많이 쓴 건 프레임워크와 ORM 메이저 업그레이드를 배포할 때였다. 배포 전에 쓰던 쿼리를 그대로 돌렸더니 배포 이후 구간이 0건으로 나왔다. 이번에도 오류는 없었다.

계측 라이브러리가 함께 올라가면서 키 이름이 바뀌어 있었다. DB span 의 SQL 은 `db.statement` 에서 `db.query.text` 로, HTTP 상태코드는 `http.status_code` 에서 `http.response.status_code` 로 옮겨갔다. 응답 시간 메트릭은 이름과 함께 단위도 ms 에서 s 로 바뀌었다.

에러율은 반대 방향으로 헷갈렸다. 배포 직후 에러 span 이 크게 줄어서, 업그레이드 덕에 뭔가 좋아진 것처럼 보였다.

4xx 가 에러 표시 대상에서 빠진 것뿐이었다. 이전 계측은 4xx 응답에도 span 에 에러 표시를 붙였는데, 새 계측은 시맨틱 컨벤션대로 5xx 만 에러로 표시한다.

그래서 배포 전후를 비교할 때는 어느 세대의 스택이 떠 있는지부터 가르도록 단계를 넣었다. 키는 두 세대를 함께 거는 필터로 조회하고, 4xx 는 에러 표시 대신 상태코드로 센다. 같은 KST 시간창을 날짜별로 잘라 비교하는 것도 규칙으로 뒀다. 48시간 평균과 오전 두어 시간을 나란히 놓으면 p99 가 세 배로 보이기 때문이다.

### 6. 스킬은 MCP 버전에도 묶여 있다

---

스킬이 묶여 있는 건 관측 키만이 아니었다. MCP 서버의 도구 이름 위에도 서 있었다.

09-11 에 서버를 v0.0.4 에서 v0.14.0 으로 교체하면서 이걸 체감했다. 도구가 21개에서 43개로 늘었고, 중간의 v0.0.5 에서 도구 이름 전체에 `signoz_` 접두사가 붙으면서 이름이 거의 다 바뀌어 있었다. 구버전의 로그 검색 도구에는 환경 필터를 걸 방법 자체가 없었다.

스킬은 v0.14 의 도구 이름으로 새로 쓰고, 구버전 바이너리는 `.bak` 으로 남겨뒀다. SigNoz 가 따로 배포하는 공식 Claude Code 스킬 묶음도 최신 도구 이름을 전제로 쓰여 있다. 결국 MCP 버전과 스킬 셋은 한 쌍으로 관리해야 했다.

그래서 로컬에 설치되어 있는 버전별로 스킬 셋을 구성해두려고 했는데, 정작 설치된 바이너리가 몇 버전인지 확인할 방법이 없었다.

```sh
$ signoz-mcp-server --version
Configuration validation failed: SIGNOZ_API_KEY is required for stdio mode
```

키 누락 오류라 키를 넣고 다시 실행했다. 이번에는 아무것도 출력되지 않고 터미널이 멈췄다. 플래그를 무시하고 stdio 서버가 그대로 떠서 입력을 기다리고 있었고, 버전은 기동 로그의 `service.version` 필드에만 찍혀 있었다.

`--version` 플래그가 처음부터 없었다.

그래서 스킬은 그동안 버전을 도구 이름으로 판정하고 있었다. `signoz_aggregate_logs` 가 보이면 v0.14 이상이다. 접두사로는 판정하지 않는다. 구버전도 일부 도구는 같은 접두사로 노출해서, 접두사만 보면 구버전이 그대로 통과한다. 통과한 Agent 는 없는 도구 대신 환경 필터 없는 구버전 도구로 알아서 대체하고, dev 가 섞인 결과를 prod 결론으로 가져온다. 2장의 크론 장면이 그대로 되풀이되는 셈이다.

교체 절차 문서에는 바이너리에서 버전 문자열을 꺼내는 `strings` 명령도 적어뒀다. 이 글을 쓰면서 다시 돌려봤더니 아무것도 출력하지 않고 정상 종료했다. 버전이 주입되는 위치를 잘못 짚은 명령이었다. 실패 신호가 없으니 한 달 동안 몰랐다.

### 7. 우회책을 쌓는 대신 업스트림을 고쳤다

---

함정 문서를 다시 읽다가 규칙이 두 종류로 갈린다는 걸 알았다. 환경 필터나 노이즈 목록은 우리 서비스의 사정이라 우리 쪽에서 알고 있어야 한다. 나머지는 도구가 실패를 알려주지 않아서 생긴 규칙이었다. 0건 응답은 시간 범위부터 의심할 것, 응답 본문이 HTML 이면 결론을 내지 말 것, 버전은 도구 이름으로 판정할 것.

뒤쪽은 MCP 서버가 고쳐지면 스킬에서 지울 수 있다. 스킬에 남겨두는 동안에는 Agent 가 매번 그 규칙을 읽고 따라야 하고, 나는 서버를 올릴 때마다 그 규칙이 아직 맞는지 다시 확인해야 한다.

그중 가장 작은 버전 플래그부터 고쳐서 PR 로 올렸다([signoz-mcp-server#347](https://github.com/SigNoz/signoz-mcp-server/pull/347)). config 를 읽기 전에 `--version` 을 먼저 처리해서, 키가 있든 없든 버전만 찍고 끝나게 했다.

처음 단 제목은 `fix: print version without requiring config` 였다. 키 누락 오류만 보고 붙인 이름이었고, 6장의 두 번째 실행은 PR 을 올린 뒤에야 해봤다. 원인이 플래그가 없는 데 있다는 걸 확인하고 `feat: add --version flag` 로 고쳤다. 조사할 때 쓰던 대조군 습관을 PR 설명에서는 건너뛰고 있었다.

처음 기여하는 계정이라 CI 는 메인테이너가 실행을 승인해야 돈다. 지금은 기다리는 중이다.

<br>
<br>

### 8. 머지되면 스킬에서 지울 수 있는 규칙들

---

버전 플래그가 들어가면 스킬의 버전 판정 단계는 명령 한 줄로 바뀌고, 동작하지 않던 `strings` 명령도 지울 수 있다.

같은 종류의 규칙이 두 개 더 있다.

구버전 백엔드에 없는 API 를 부르면 대시보드 목록 도구가 SigNoz 웹 화면의 HTML 을 성공 응답으로 돌려준다. Agent 입장에서는 대시보드가 하나도 없다는 답과 구분하기 어렵다. 스킬은 지금 "응답이 `<` 로 시작하면 결론을 내지 말 것" 이라는 규칙으로 막고 있다.

0건 응답도 비슷하다. 백엔드 응답에는 스캔한 행 수(`rowsScanned`)가 들어 있는데 도구 응답에는 실리지 않는다. 이 값이 실리면 2장의 1년 틀린 쿼리는 Agent 가 스스로 의심할 수 있다.

둘 다 도구의 응답 모양이 바뀌는 변경이라 첫 PR 보다 리뷰 부담이 크다. 첫 PR 이 머지되는 걸 보고 하나씩 올려볼 생각이다.

## 🤔 Understanding

- **스킬은 순서를, 문서는 이유를 담는다** — 함정을 스킬 본문에 섞지 않고 별도 문서로 빼두니, 함정이 늘어도 스킬의 흐름은 그대로 유지됐다.
- **스킬은 관측 키와 도구 계약 위에 서 있다** — 계측 라이브러리가 바뀌면 키가, MCP 서버가 바뀌면 도구 이름이 바뀐다. 둘 다 오류 없이 0건으로 드러나서, 스킬이 어느 버전을 전제로 하는지 확인할 수단이 필요했다.
- **도구 때문에 생긴 우회책은 따로 모아둔다** — 도구 때문에 생긴 규칙은 업스트림이 고쳐지면 지울 수 있다. 그 규칙들을 따로 모아두니 기여할 거리가 자연스럽게 정해졌다.
